About / working method

Technical credibility comes from a visible boundary.

Z3X-1337 is the public work surface for Zaid Hijazi: security-focused software, concise educational notes, and projects that document what they do and where they stop.

01 / Method

A working sequence for reviewable security work.

The exact process changes with the system, but the public projects share the same preference: understand the boundary, preserve evidence, make automation explainable, and keep the limitations in the output.

01 / FRAME

Define the boundary

Name the user, action, resource, operating context, and scope before declaring what a system should enforce or observe.

02 / PRESERVE

Keep evidence intact

Store source context, normalized data, the rule that fired, and uncertainty so another reviewer has a path to validate or dismiss it.

03 / EXPLAIN

Make the result inspectable

Prefer deterministic rules, visible thresholds, and output that describes what was observed without silently escalating it into impact.

04 / CONSTRAIN

Bound authority

For systems that act, keep permissions, policy, confirmations, and receipt handling outside unrestricted natural-language control.

05 / VERIFY

Test the claim

Use automated tests, review paths, and isolated examples to verify the narrow behavior being represented—not a broader claim by implication.

06 / REPORT

State the limit

Separate a demonstrable observation, a hypothesis, and a conclusion. If evidence is missing, say what would be needed.

02 / Responsible scope

No findings without evidence.

This site does not claim CVEs, client work, third-party access, bounty outcomes, or exploit impact. Educational notes use generalized and illustrative examples. Any authorized security review should use stated scope, controlled data, and the minimum-impact validation needed to support a conclusion.

The projects are public so their implementation, tests, documentation, and stated constraints can be read at the source.
