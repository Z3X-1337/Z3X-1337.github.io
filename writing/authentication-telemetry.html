SOC / telemetry / field note 02

Authentication telemetry needs context.

Repeated failures are useful signals for analyst review. They only become meaningful when they are paired with identity, source, method, time, and subsequent behavior.

Zaid Hijazi13 Aug 202605 min read

On this page

Authentication logs are full of repeatable patterns: failed passwords, invalid usernames, unsupported methods, successful logins, and source addresses. A parser can count these events quickly. The harder work is deciding what the count does and does not mean.

A signal is not a verdict

A burst of failures from one address may warrant review. It may also come from a user with an outdated client, a misconfigured service, a NAT gateway, a scanner in an authorized environment, or an event that cannot be resolved from the available log source.

Good defensive tooling keeps that distinction visible. It reports the observation and the reason it crossed a configured threshold; it does not quietly convert a pattern into an assertion of malicious intent.

Context that changes the review

Useful review begins by connecting the raw event to a sequence. The following redacted, illustrative fragment contains a source, a user pattern, a method, and a later event to investigate.

2026-08-13T08:14:02Z failed  user=admin       source=198.51.100.42 method=password
2026-08-13T08:14:07Z failed  user=deploy      source=198.51.100.42 method=password
2026-08-13T08:14:15Z failed  user=backup      source=198.51.100.42 method=password
2026-08-13T08:21:43Z accepted user=known-user  source=198.51.100.42 method=publickey

This does not establish a conclusion. It gives an analyst concrete questions: are the accounts expected, did the source appear elsewhere, does the successful login belong to a known identity, and what surrounding telemetry is available?

  • Source: address, network context, and whether address sharing is plausible.
  • Identity: user names, invalid accounts, and any later successful authentication.
  • Method: password, public key, keyboard-interactive, or another supported event type.
  • Time: event ordering and the window in which the sequence occurred.
  • Coverage: what the parser supports and what it cannot see.

Thresholds should stay explainable

Thresholds can make a large dataset reviewable, but the threshold must be shown alongside the result. If a rule marks repeated failures after five events, a report should say so. If a password-spray-style heuristic looks for multiple usernames from the same source, the output should expose the accounts and count that triggered it.

Working rule

A detection is an evidence-backed hypothesis for analyst review. Its threshold, supporting events, and limitations should remain visible in the output.

Output for a human reviewer

Auth Log Analyzer produces JSON and Markdown findings for supported OpenSSH events. Its purpose is to reduce the distance between raw logs and a reviewable observation — not to replace a broader investigation.

That is why structured output matters. A report that retains the source, count, affected usernames, event types, and explanatory rationale gives the next reviewer a path to validate or dismiss the signal responsibly.
