Authorization is a server-side decision.

A hidden control, a client-side role check, or a predictable resource URL does not prove that an actor is allowed to do something. The server must decide.

Zaid Hijazi13 Aug 202604 min read

On this page

Application interfaces are designed for convenience. They show relevant actions, hide irrelevant ones, and often hold state in the browser. None of that should be confused with authorization. A browser is controlled by the user; the enforcement decision must be made by the service that owns the protected resource or operation.

UI is not the boundary

Removing an “edit” button is a product decision. It can make a normal workflow clearer, but it does not establish permission enforcement. A client can request a URL or API operation regardless of whether the interface chose to render a control.

The same applies to client-side flags. A value such as isAdmin may help the interface decide what to show. It is not a trustworthy basis for deciding whether a protected action is allowed.

What the decision needs

A useful way to reason about authorization is to name the parts of the decision explicitly:

actor    = authenticated identity and effective role
action   = requested operation
resource = object or record being accessed
boundary = organization, tenant, ownership, or policy scope

allow only when the server validates the complete relationship

A role alone may not be enough. A user can have a valid role in one organization but not another. A resource can be visible but not mutable. An operation can require a different policy than the adjacent read endpoint. Naming these relationships helps make both the code and the review sharper.

Model the workflow

For an authorized design review or test, start by understanding the intended workflow: users, roles, organizations, resources, ownership, and state transitions. Then ask which server-side check protects each sensitive operation.

  • Which actor is authenticated, and what authority is active?
  • Which resource is being read or changed?
  • Does the resource belong to the actor's allowed organization or scope?
  • Does the requested action require a stronger permission than viewing?
  • Does the server make this decision independently of browser state?

Review language

Describe the missing or effective server-side check precisely. Do not treat a visible UI condition as proof of enforcement or as proof of a vulnerability.

Keep authorized tests controlled

When a program explicitly authorizes testing, controlled accounts and controlled data are the right way to validate permission boundaries. The aim is to prove the smallest meaningful impact needed for the report, not to collect unrelated data or extend access beyond the approved scope.

This is a general security principle, not a claim about a third-party application or a public finding. Clear scope, clear evidence, and minimal-impact validation are how research stays useful and responsible.
