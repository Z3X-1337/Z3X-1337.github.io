Web security / field note 01

Security headers are control surfaces, not checkbox evidence.

A header's presence is one observation. A useful review follows the response, the policy, and the actual route behavior before it reaches a conclusion.

Zaid Hijazi13 Aug 202604 min read

On this page

Presence is a starting point Review the response path Read the policy, not just the name A review matrix Report the observation precisely

Security headers are often presented as a simple list: present or absent. That is useful for inventory, but it is too thin to describe the security effect of a web response. A meaningful review asks what a particular response does, where the browser receives it, and whether the policy fits the application's behavior.

Presence is a starting point

Seeing Content-Security-Policy, Strict-Transport-Security, or X-Content-Type-Options is better than seeing nothing at all. It is not proof that the application has been protected against every relevant class of issue.

For example, a Content Security Policy can be present while still permitting broad script sources, unsafe execution behavior, or legacy allowances that deserve closer review. The appropriate conclusion is not “secure” or “insecure” from the header name alone; it is a specific observation about the directives received on a specific response.

Review the response path

Redirects and status-specific behavior matter. A browser may visit an initial URL, receive a redirect, and finally process a different response. Error pages, login pages, and application routes can have distinct header sets too.

$ security-header-auditor https://example.test/account
request  GET https://example.test/account
redirect 302 → https://example.test/login
final    200 /login

observed headers
  strict-transport-security: max-age=31536000
  content-security-policy: default-src 'self'; object-src 'none'
  x-content-type-options: nosniff

The example is illustrative, but the question is real: which response should the reviewer describe, and which route is actually relevant to the user's flow? Document the redirect chain and avoid silently treating the first response as the whole story.

Read the policy, not just the name

Policies are configuration. Their directives are the substance of the control. A reviewer can record the effective directives, distinguish unknown from absent behavior, and note where a manual browser check or application-context review would be needed.

  • Record the URL and response status that produced the observation.
  • Follow allowed redirects and retain the final URL.
  • Preserve the relevant header value rather than only a boolean result.
  • Separate an automated observation from claims about exploitability or business impact.

A review matrix

A concise report can make the boundary of the observation clear without losing the useful detail:

ObservedSupportsDoes not establish
A selected header is absent from the final response.A reproducible configuration observation for that route.Exploitability, severity, or behavior across every route.
A CSP directive appears in the response.An exact policy record suitable for further review.That every application feature is protected as intended.
A redirect chain reaches a different final URL.The relevant response context for the observed flow.That unrelated flows or error responses share the same controls.

A useful boundary

An automated header review can identify configuration evidence. It cannot, by itself, demonstrate how every browser, route, integration, or application feature behaves.

Report the observation precisely

A good report lets another reviewer reproduce the same request and understand what was observed. “CSP missing on the final login response after an HTTPS redirect” is clearer than a generic score. So is “CSP present with these directives; application-level policy effect not independently validated.”

That precision also keeps security tooling honest. Security Header Auditor is designed for authorized targets and deterministic response observations; it does not turn a header checklist into an unsupported vulnerability claim.
