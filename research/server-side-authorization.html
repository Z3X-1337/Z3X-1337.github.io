Note 02 / Application security

Authorization is a server-side decision.

A hidden control, client-side role check, or predictable URL does not show that an actor is allowed to do something. The service that owns the operation must decide.

By Zaid Hijazi13 August 20264 min read

Interfaces are designed for convenience. They show relevant actions, hide irrelevant ones, and frequently hold state in the browser. None of that should be confused with authorization. A client is controlled by the user; enforcement belongs with the service that owns a protected resource or operation.

UI is not the boundary.

Removing an edit button can make a normal workflow clearer. It does not establish that the action is forbidden. Likewise, a client-side value such as isAdmin may be useful for presentation while being an unsafe basis for a service-side permission decision.

A useful design review therefore distinguishes what the interface suggests from what the service actually validates. The second question determines whether the operation is protected.

Name the complete decision.

Authorization becomes easier to reason about when the relevant parts of the decision are explicit.

actor     authenticated identity and effective role
action    requested operation
resource  object or record being accessed
boundary  organization, tenant, ownership, or policy scope

allow only when the service validates the complete relationship

A role alone may not be enough. A user can be authorized in one organization but not another. A resource can be visible but not mutable. An adjacent read operation can be protected by a different rule than a sensitive write. Naming these relationships makes both design and review more precise.

Model the intended workflow.

For an authorized design review or assessment, start with the intended model: users, roles, organizations, resources, ownership, and state transitions. Then ask which service-side check protects each sensitive operation.

  • Which identity is authenticated, and what authority is active?
  • Which record, operation, or state transition is requested?
  • Does the resource belong to the actor’s allowed organization, tenant, or ownership scope?
  • Does this operation require a stronger permission than viewing the surrounding data?
  • Is the decision made independently of browser state?

Review language

Describe the effective or missing service-side check precisely. A visible interface condition is neither proof of enforcement nor proof of a vulnerability by itself.

Keep validation controlled.

When a program explicitly authorizes testing, controlled accounts and controlled data are the appropriate way to validate a permission boundary. The aim is to prove the smallest meaningful impact necessary for a report, not to collect unrelated data or extend access beyond approved scope.

This note is a general application-security principle. It does not refer to a third-party application or claim a personal finding. Scope, evidence, and minimum-impact validation are what make research both useful and responsible.

Where it connects to public work.

The public repositories Rayluno, ToxicJoin, and Unwritten approach a related engineering concern: let natural-language systems propose, while deterministic policy, approval, and bounded execution decide what can happen.
